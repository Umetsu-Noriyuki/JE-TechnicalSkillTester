# プログラミングスキル判定テスト Webアプリケーション仕様書

- 版数：v2.0（Google Apps Script前提版）
- 対象読者：開発担当者、企画・人事担当者

---

## 1. 目的

IT業界未経験者〜入社3年目までの社員を対象に、プログラミング・SQL・ロジカルシンキング・行動指針に関する知識・考え方をWeb上で判定するテストを提供する。取得したデータを用いて、以下を実現する。

- 入社希望者に対する技量判断（採用選考の参考情報）
- 若手社員の苦手分野の把握と教育計画への反映

---

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| GAS | Google Apps Script。本システムのサーバーサイド処理・Webアプリ公開に使用する。 |

## 3. システム構成（Google Apps Script前提）

### 3-1. 全体構成

本システムは、**Google Apps Script（GAS）** を実装基盤とすることを前提とする。

- **フロントエンド**：GASの `HtmlService` によって配信するHTML／CSS／JavaScript（受験画面・結果画面等）。
- **バックエンド**：GASのサーバーサイド関数（.gsファイル）。問題の抽出、採点、記録処理を担う。
- **データストア**：Googleスプレッドシート。最低限、以下3シートで構成する。
  1. 「問題マスタ」シート（出題データ、72問）
  2. 「受験結果」シート（受験者ごとの結果を1行ずつ蓄積）
  3. 「受験許可」シート（入社希望者に対し受験を許可する氏名の一覧、6-3章）

```
                 ┌────────────────────────┐
受験者ブラウザ ───▶│ GAS Webアプリ (doGet)   │
                 │  ・role判定             │
                 │  ・HTML(HtmlService)配信 │
                 └───────────┬────────────┘
                             │ google.script.run
                 ┌───────────▼────────────┐
                 │ GASサーバーサイド関数     │
                 │ ・受験許可判定 / 問題抽出 │
                 │ ・採点 / 記録            │
                 └───────────┬────────────┘
                             │ SpreadsheetApp
                 ┌───────────▼────────────┐
                 │ Googleスプレッドシート    │
                 │ ・問題マスタ シート       │
                 │ ・受験結果 シート         │
                 │ ・受験許可 シート         │
                 └────────────────────────┘
```

### 3-2. データソースとしてのGoogleスプレッドシート

- 問題バンク（72問以上）は、GASから参照するGoogleスプレッドシート「問題マスタ」シートに保持する（データ構造は7-1参照）。
- GASは `SpreadsheetApp.openById(SHEET_ID)` 等でスプレッドシートを取得し、シート内容を読み込んで出題データとして利用する。
- 問題の追加・修正・削除は、コードを変更せず「問題マスタ」シートの編集のみで行える構成とする。

### 3-3. 開発方法

- Typescriptでコードを作成し、RollupによりJavaScriptにトランスパイル、claspでデプロイする方式とする。

### 3-4. Webアプリとしての公開方法

- 本システムは、GASの「ウェブアプリとしてデプロイ」機能を用いて公開する。
- `doGet(e)` 関数がHTTPリクエストを受け付け、URLパラメータ（`role`）に応じて表示するHTMLを出し分ける（4-1参照）。

```javascript
// Code.gs（イメージ）
function doGet(e) {
  var role = e.parameter.role;
  var validRoles = ['applicant', 'newhire', 'junior'];

  if (validRoles.indexOf(role) === -1) {
    return HtmlService.createHtmlOutput(
      '<p>このページには、管理者から案内された専用URLからアクセスしてください。</p>'
    );
  }

  var template = HtmlService.createTemplateFromFile('Index');
  template.role = role;
  return template.evaluate()
    .setTitle('プログラミングスキル判定テスト')
    .addMetaTag('viewport', 'width=device-width, initial-scale=1');
}
```

- デプロイ設定について、入社希望者（組織外の人）もアクセスする想定であるため、「アクセスできるユーザー」は「全員」とする必要がある。
- この場合、スクリプトは「実行するユーザー＝デプロイした本人（またはデプロイ設定で指定したアカウント）」の権限で動作するため、スプレッドシートへの読み書き権限はそのアカウントに紐づく。デプロイ担当アカウントの管理（退職時の引き継ぎ等）に留意する。

## 4. 受験者区分と権限差異

### 4-1. 受験者区分の指定方法（URLパラメータ方式）

受験者区分は、受験者自身に選択させるのではなく、**管理者があらかじめ発行するURLのクエリパラメータによって指定する。**

| パラメータ名 | 値 | 対応する受験者区分 |
|---|---|---|
| `role` | `applicant` | 入社希望者 |
| `role` | `newhire` | 未経験の新入社員 |
| `role` | `junior` | 入社3年目までの社員 |

例（`XXXX` はGASのデプロイID）：

- 入社希望者向け：`https://script.google.com/macros/s/XXXX/exec?role=applicant`
- 未経験の新入社員向け：`https://script.google.com/macros/s/XXXX/exec?role=newhire`
- 入社3年目までの社員向け：`https://script.google.com/macros/s/XXXX/exec?role=junior`

**サーバーサイドでの検証（GASならではの利点）**

- `role` パラメータの検証は、`doGet(e)` 関数内、すなわち**サーバーサイド（GAS実行環境）** で行う（3-3のコード例参照）。
- 検証はブラウザにHTMLが届く前に行われるため、ブラウザの開発者ツールでクライアント側の変数を書き換えても、サーバー側の判定結果そのものを覆すことはできない。
- 判定の結果、`role` が不正・未指定の場合は、開始画面を含む本来のHTMLを一切返却せず、案内メッセージのみのHTMLを返す。

**限界事項（重要）**

- サーバーサイドで検証するとはいえ、`role` の値自体はURLというユーザーが自由に書き換えられる場所に置かれている。そのため、受験者がURLの `role` の値を別の区分の値に書き換えてアクセスすることは技術的に可能であり、なりすまし対策としては限定的である。
- 厳密な不正防止（本人以外が別区分のURLを推測・使い回しできないようにする）が必要な場合は、14章の拡張案にある「発行済みトークン方式」への拡張を検討すること。

### 4-2. 受験者区分ごとの権限差異

| 受験者区分 | 社員番号入力 | 所属入力 | 終了時の操作 | 正解率の表示 |
|---|---|---|---|---|
| 入社希望者 | 非表示 | 非表示 | 「回答終了」ボタン | 表示しない |
| 未経験の新入社員 | 表示 | 表示 | 「採点」ボタン | 表示する |
| 入社3年目までの社員 | 表示 | 表示 | 「採点」ボタン | 表示する |

- 「未経験の新入社員」と「入社3年目までの社員」は、画面上の挙動（項目表示・ボタン・結果表示）は同一とする。記録データ上の受験者区分としてのみ区別し、教育計画立案時の分析に用いる。

### 5-1. 管理者による結果確認

- 受験結果はGoogleスプレッドシート「受験結果」シートに直接蓄積されるため、管理者はスプレッドシートを開くだけで、フィルタ・ソート・ピボットテーブルなどGoogleスプレッドシート標準機能を使って集計・分析できる。専用の管理画面（Web UI）を別途作り込む必要は必須ではない。
- 簡易な集計ビュー（区分別の平均正解率など）をWebアプリ内に用意したい場合は、`doGet(e)` に管理者向けの別パラメータ（例：`?admin=1`）を用意し、`Session.getActiveUser().getEmail()` で取得したアクセス者のメールアドレスが、あらかじめ定めた管理者リストに含まれる場合のみ集計結果を表示する、といった実装とする（本仕様ではオプション機能とする）。

## 6. 開始画面 仕様

### 6-1. 入力項目

受験者区分は、開始画面に到達する前の時点でURLパラメータ（4-1参照）によりサーバーサイドで確定している。そのため、開始画面には受験者区分を選択・変更するUIは設けず、確定済みの区分に応じて以下の項目の表示・非表示を自動的に切り替える。

| 項目名 | 入力形式 | 必須 | 表示条件 | 備考 |
|---|---|---|---|---|
| 氏名 | テキストボックス | 必須 | 常時表示 | 全角・半角どちらも許容。 |
| 社員番号 | テキストボックス | 必須 | URLパラメータの区分が「入社希望者」以外のとき表示 | 半角英数字を想定。 |
| 所属 | テキストボックス | 必須 | URLパラメータの区分が「入社希望者」以外のとき表示 | 全角・半角どちらも許容。 |

- 確定した受験者区分を「〇〇として受験します」等の形で画面上に表示し、受験者が誤ったURLを案内されていないか気づける状態にすることが望ましい。

### 6-2. 画面上の説明表示

- 出題数（全30問）、出題形式（選択式はチェックボックスから1つ選択、記述式はテキスト入力）、制限時間（30分）を開始前に受験者へ明示する。
- 「テスト開始」ボタン押下時に必須項目の入力チェックを行い、未入力があればエラーメッセージを表示して開始しない。

### 6-3. 受験許可チェック（入社希望者のみ）

URLを知っている者であれば誰でも際限なくテストを受験できてしまう状態を防ぐため、**入社希望者**についてのみ、あらかじめ許可された氏名でなければテストを開始できないようにする。未経験の新入社員・入社3年目までの社員は、自己学習のために複数回受験することを妨げない方針とし、本チェックの対象外とする（社員による悪意あるアクセスは想定しない業務判断による）。

- 問題マスタ・受験結果と同じGoogleスプレッドシート内に「受験許可」シートを用意する。A列2行目以降に、受験を許可する氏名（入社希望者のみ）を1行1名で記載する（1行目はヘッダー行）。
- **受験者区分が「入社希望者」の場合のみ**、「テスト開始」ボタン押下時に6-1で入力された氏名と「受験許可」シートに記載された氏名を突き合わせる。
  - 比較は、双方の文字列に含まれる半角スペース・全角スペースを全て除去したうえで、完全一致で行う（例：「山田　太郎」と「山田 太郎」は一致とみなす）。
- 一致する氏名が存在しない場合、画面に「＜入力された氏名＞様は受験を許可されていません。」というメッセージを表示し、テストを開始しない（表示する氏名は正規化前の入力値そのものとする）。
- **受験者区分が「未経験の新入社員」「入社3年目までの社員」の場合、本チェックは行わない。** 6-1の必須項目入力チェックのみでテストを開始できる。
- なりすまし対策としては限定的である `role` パラメータ方式（4-1章）と同様、クライアント側JavaScriptでの事前チェックに加え、クライアント側の改ざんによる回避を防ぐため**サーバーサイドの関数でも同じ判定を行う**（例：`getQuizQuestions(role, name)` のように入力氏名をサーバーへ送り、`role` が入社希望者の場合のみ氏名の許可判定を行ったうえで問題データを返却する）。
- 「受験許可」シートに氏名が存在しない場合（入社希望者のみ）、問題の抽出・出題は一切行わない。

**限界事項**

- 本チェックは「入力された氏名が受験許可シートに存在するか」のみを判定するものであり、受験回数そのものを制限する仕組みではない。そのため、許可された氏名を知る本人（または同姓同名の第三者）が同じURLへ繰り返しアクセスし、複数回受験することは技術的に防止できない。受験回数そのものを制限する必要がある場合は、14章に記載のトークン方式等への拡張を検討すること。
- 社員（未経験の新入社員／入社3年目までの社員）は本チェックの対象外であるため、URLを知っていれば誰でも何度でも受験可能である。これは意図した仕様であり、社員による不正アクセスは想定しないという業務判断に基づく。

### 6-4. 開始時の処理

1. 受験者が「テスト開始」ボタンを押下すると、受験者区分が「入社希望者」の場合のみ6-3の受験許可チェックを行う。許可されない場合は6-3の通りエラーメッセージを表示し、以降の処理を行わない（入社希望者以外の場合は本ステップを行わずステップ2へ進む）。
2. クライアントJavaScriptから `google.script.run.withSuccessHandler(...).getQuizQuestions(role, name)` を呼び出す。
3. サーバーサイド関数 `getQuizQuestions(role, name)` は、`role` が入社希望者の場合のみ受験許可チェック（6-3章）を行ったうえで「問題マスタ」シートを読み込み、出題ロジック（7章）に従い30問を抽出し、各問題の選択肢の表示順をシャッフルした上で、問題セット（JSON相当のオブジェクト）をクライアントに返却する。
4. クライアントは受け取った問題セットをもとに1問目を表示し、試験開始時刻を記録してタイマーを起動する（9章）。

## 7. 出題ロジック仕様

### 7-1. 問題マスタ（スプレッドシート）のデータ構造

「問題マスタ」シートは、1行につき1問を保持する。想定する列構成は以下の通り（1行目はヘッダー行）。

| 列 | 項目 | 内容 |
|---|---|---|
| A | 問題ID | 一意の識別子（例：`cod-if-01`）。受験結果シートとの突き合わせに使用。 |
| B | 区分 | 大区分名（コーディング／SQL／プログラミング技法／ロジカルシンキング／行動指針）。 |
| C | 小区分 | 小区分名（例：if文の条件式）。 |
| D | 出題形式 | `choice`（選択式）または `text`（記述式）。 |
| E | 問題文 | 出題文。 |
| F〜I | 選択肢1〜4 | 選択式の場合のみ使用。記述式の場合は空欄。 |
| J | 正解番号 | 選択式の場合のみ使用。選択肢1〜4のうち正解の列番号（1〜4）。 |
| K | 模範回答 | 記述式の場合のみ使用。 |
| L | 備考 | 出題意図等の補足（受験者には非表示、管理者・出題担当者向け）。 |

- GASは `getDataRange().getValues()` 等でシート全体を読み込み、各行を上記の構造に沿ったオブジェクトへ変換した上で7-2以降の抽出処理を行う。

### 7-2. 抽出単位

区分（大分類）ごとに6問ずつ、5区分合計30問を抽出する。

| 区分 | 問題マスタ内の問題数（本仕様策定時点） | 抽出数 |
|---|---|---|
| コーディング | 39問 | 6問 |
| SQL | 6問 | 6問（全問採用） |
| プログラミング技法 | 6問 | 6問（全問採用） |
| ロジカルシンキング | 6問 | 6問（全問採用） |
| 行動指針 | 15問 | 6問 |
| **合計** | **72問** | **30問** |

- 区分内の問題数が抽出数（6問）以下の場合は、その区分の全問を採用し、出題順のみランダムにする。
- 区分内の問題数が抽出数を超える場合（コーディング・行動指針）は、以下7-3の方法でランダム抽出する。

### 7-3. 記述式問題の配分（コーディング区分の例）

「記述式もまんべんなく入るように」という要件に対応するため、対象区分内の「選択式問題数」と「記述式問題数」の構成比に応じて、抽出数（6問）を按分する。

1. 対象区分内の記述式問題の比率を求める（記述式問題数 ÷ 区分内の全問題数）。
2. 抽出数6問にその比率を掛け、四捨五入して「記述式の抽出目標数」とする。ただし、区分内に記述式が1問以上存在する場合は目標数を最低1問とする。
3. 残りを「選択式の抽出目標数」とする。
4. 記述式・選択式それぞれのプールからランダムに目標数を抽出し、両者を合わせた上で出題順をランダムにする。

例：コーディング区分（全39問、うち記述式11問・選択式28問）の場合、記述式目標数は 6 ×(11/39) ≈ 1.7 → 2問、選択式は4問となる。

- 行動指針区分は問題マスタ内に記述式問題が存在しないため、6問すべて選択式から抽出する。
- 乱数の生成にはGASの `Math.random()` を用いる。

### 7-4. 出題順序

- 全30問は、区分ごとにまとめず、抽出後にシャッフルして出題する（区分名は受験者に開示しない）。
- 各問題には内部的に「区分」「小区分」を保持し、採点時の集計にのみ使用する。

## 8. 選択肢のランダム表示仕様

- 選択式問題の4つの選択肢は、`getQuizQuestions` 関数がサーバーサイドで返却する時点で、表示順をランダムに入れ替える（同一問題が別受験者・別回に出題された際、選択肢の並びが固定化しないようにするため）。
- シャッフル後も、各選択肢が「元のどの選択肢か（正解かどうか）」の対応情報は、サーバーサイドの一時データ（後述10章の採点処理用）または各選択肢に付与した正誤フラグとして保持し、選択された選択肢の表示位置ではなく、対応する正誤フラグに基づいて採点する。これにより、選択肢の順序を入れ替えても採点結果に誤りが生じないようにする。
- 1問につき正解は1つとする（複数正解問題は本仕様の対象外）。

## 9. 制限時間・経過時間表示仕様

### 9-1. 試験時間

- 制限時間は**30分**とする。
- 受験画面の表示開始時点（開始画面で「テスト開始」を押下し、`getQuizQuestions` の結果を受け取った時点）から計測を開始する。

### 9-2. 経過時間の表示

- 受験画面には、常時「経過時間」を表示する（例：`経過時間 12:34 / 制限時間 30:00`）。
- 表示形式は「分:秒」（mm:ss）とし、クライアント側JavaScriptの `setInterval` 等で1秒ごとに更新する。
- 残り時間が一定値（例：残り5分）を切った場合、表示色を変える等して受験者に視覚的な注意喚起を行う（詳細な閾値・配色は実装時に調整可）。

### 9-3. 時間切れ時の挙動

制限時間（30分）に達した時点で、クライアント側で以下を自動的に行う。

1. 全ての選択肢（チェックボックス）およびテキスト入力欄を操作不可（disabled）状態にする。すでに入力・選択済みの内容はそのまま保持する。
2. 問題間のページ送り（前へ／次へ、問題番号ジャンプ等）による回答内容の変更操作も無効化する。
3. 受験者区分に応じて、次のいずれかのボタンのみをクリック可能な状態にする。
   - 入社希望者：「回答終了」ボタン
   - 社員（未経験の新入社員／入社3年目までの社員）：「採点」ボタン
4. 時間切れになった旨を画面上に明示する（例：「制限時間に達しました。ここまでの回答内容で終了します。」等のメッセージ表示）。

### 9-4. 時間内終了時の挙動

- 制限時間内に受験者が自ら「採点」または「回答終了」ボタンを押した場合は、9-3の時間切れ処理と同様に以降の入力を無効化した上で、10章の採点処理・11章の記録処理に進む。
- 制限時間に達した場合でも、ボタン押下は受験者自身の操作を必要とし、自動的に採点・記録処理を行うことはしない（受験者が最終確認の上でボタンを押す運用とする）。

## 10. 採点仕様

### 10-1. 採点処理の実行場所と非同期化

- 採点処理は、クライアント側JavaScriptではなく、**GASのサーバーサイド関数**で行う。
- 「採点」または「回答終了」ボタン押下時、クライアントは受験者の全回答（選択式の選択内容、記述式の入力内容）を `payload` としてサーバーサイド関数に送信する。
- 記述式の採点（10-2章）はGemini APIの呼び出しを伴い数分単位の時間がかかるため、受験者を待たせないよう、採点処理を次の2段階に分ける。

| 段階 | 関数 | 内容 |
|---|---|---|
| ① 即時処理 | `submitResult(payload)` | 選択式の採点、記述式の提出内容の記録（採点は未実施）を行い、「受験結果」シートへ1行追記したうえで、その行番号（`resultId`）と選択式のみを集計した暫定の採点結果を即座にクライアントへ返す。記述式の該当セル（11-2章 N〜T列）には「採点中」を仮に記録する。 |
| ② バックグラウンド処理 | `scoreDescriptiveQuestions(resultId, payload)` | ①の完了後、クライアントが間を置かずに呼び出す。記述式問題の採点（10-2章）を行い、選択式と合わせた最終的な採点結果で「受験結果」シートの該当行（F〜K列・M〜T列）を上書きする。 |

- クライアントは①の応答を受け取り次第、結果画面／終了画面へ切り替えて表示する（この時点の正解率は選択式のみの暫定値、10-3章）。続けて②をフォアグラウンドで待たずに呼び出し（fire-and-forget）、完了状況をポーリング（`getDescriptiveScoringStatus(resultId)`）で確認する。
- GASのサーバー側実行は、呼び出し元のクライアントとの接続状態と独立して継続する。そのため、②の呼び出し後に受験者が画面を閉じたりブラウザを閉じたりしても、②の処理はサーバー側で最後まで実行され、採点結果は従来どおり「受験結果」シートに記録される。
- ②の完了をクライアントが検知したら、最終結果取得用の `getDescriptiveScoringResult(resultId, payload)` を1回だけ呼び出し、画面表示中の正解率・分野別正解率を最終値へ更新する（10-4章）。
- 採点をサーバーサイドで行うことで、クライアント側のJavaScriptやブラウザの通信内容を書き換えることによる不正な点数操作を防止する（①②とも同様）。

### 10-2. 記述式の採点

- 選択式問題は、選択された選択肢と正解番号の一致により自動採点する（10-1章）。
- 記述式問題は、Gemini API（Google AI Studio で発行した API keyを使用）を利用し採点する。
- **出題される記述式問題（最大7問）は、1問ずつではなく、まとめて1回のリクエストでGeminiに採点させる。** レート制限（1分あたりのリクエスト数上限）に達しにくくするための対応であり、Geminiには `specification/for-AI-prompt.md` のプロンプトで、複数設問分の採点結果をまとめて返すよう指示する。
- 各問題毎に100点満点で採点する。
- 未回答の記述式問題は、Geminiへの採点依頼の対象から除外し0点とする（`for-AI-prompt.md` 自体も「回答無しの場合は0点」と定義しているため）。全問未回答の場合はAPIを呼び出さない。
- Gemini呼び出しが失敗した場合（レート制限・一時的な過負荷等）は、一定時間待機したうえで最大3回まで再試行する（合計最大4回試行）。1回のリクエストに全問をまとめているため、再試行を尽くしても失敗した場合は、その回に出題された記述式問題全問が0点として扱われる（12章参照）。

### 10-3. 正解率の算出

選択式・記述式の両方を得点化したうえで、正解率を算出する。

| 出題形式 | 得点化の方法 |
|---|---|
| 選択式 | 正解の場合100点、不正解（未回答含む）の場合0点 |
| 記述式 | Gemini APIによる採点結果（0〜100点、10-2章）。API呼び出しが失敗した場合も0点として扱う（12章参照） |

| 項目 | 算出方法 |
|---|---|
| 総合正解率 | 出題された全問題（選択式＋記述式）の得点合計 ÷ 出題総数 |
| 区分別正解率 | 区分ごとに、その区分内で出題された問題（選択式＋記述式）の得点合計 ÷ その区分の出題数 |

- 正解率の値に小数点以下が含まれる場合は、小数点以下を四捨五入した整数値とする。
- 10-1章の非同期化に伴い、正解率は次の2段階で算出・表示される。
  1. `submitResult` の応答時点：選択式のみを対象に算出した暫定値。
  2. `scoreDescriptiveQuestions` 完了後（`getDescriptiveScoringResult` 取得時点）：選択式＋記述式を対象に算出した最終値。画面表示中の値をこの最終値で置き換える（10-4章）。
- 記述式問題ごとのGemini採点結果（得点・フィードバック）は、11-2章の回答詳細（M列）・記述式採点列（N〜T列）に記録する。

### 10-4. 結果表示（社員のみ）

- 未経験の新入社員／入社3年目までの社員：`submitResult` から返却された暫定の採点結果（選択式のみの総合正解率・区分別正解率）をまず画面表示し、その下に「記述式の採点結果」セクションを設ける。
  - 「記述式の採点結果」セクションには、採点完了までスピナー（採点中であることを示す表示）と「すべての記述式が採点されるまで10～15分かかります」という案内文を表示する。
  - `getDescriptiveScoringResult` により最終結果を取得できたら、記述式問題1問ごとに、入力回答・スコア・参考回答（模範回答）・フィードバックを表示し、あわせて総合正解率・分野別正解率の表示を最終値（選択式＋記述式）へ更新する。
  - 出題された記述式問題が0問の場合は、この「記述式の採点結果」セクション自体を表示しない。
- 入社希望者：サーバー側では社員と同様に採点・記録処理（①②とも）を行うが、クライアントは採点結果を画面に表示せず、結果を伏せたお礼・終了メッセージのみを表示する。

## 11. データ記録仕様（Googleスプレッドシートへの記録）

### 11-1. 記録タイミング

10-1章の非同期化に伴い、1回分の受験結果は次の2段階で「受験結果」シートへ記録する。

1. 「採点」または「回答終了」ボタン押下時点（9-3・9-4の処理後）に、サーバーサイド関数 `submitResult(payload)` 内で、選択式の採点結果・記述式の提出内容（採点は未実施、N〜T列は「採点中」の仮値）で1行追記する。
2. その後、バックグラウンド処理 `scoreDescriptiveQuestions(resultId, payload)` 内で、記述式の採点完了後に同じ行（F〜K列・M〜T列）を最終値で上書きする。

### 11-2. 記録項目（「受験結果」シートの列構成）

| 列 | 項目 | 内容 |
|---|---|---|
| A | 記録日時 | `new Date()` 等、サーバー側の現在日時（テスト終了時点）。段階2では更新しない。 |
| B | 受験者区分 | 入社希望者／未経験の新入社員／入社3年目までの社員。段階2では更新しない。 |
| C | 氏名 | 開始画面での入力値。段階2では更新しない。 |
| D | 社員番号 | 開始画面での入力値（入社希望者の場合は空欄）。段階2では更新しない。 |
| E | 所属 | 開始画面での入力値（入社希望者の場合は空欄）。段階2では更新しない。 |
| F | 総合正解率 | 10-3の算出結果（入社希望者にも記録する。画面表示のみ行わない）。段階1では選択式のみの暫定値、段階2で選択式＋記述式の最終値に上書きする。 |
| G〜K | 区分別正解率（5区分分） | 区分ごとの正解率（10-3章、選択式・記述式を得点化した平均）・出題数・得点合計。F列と同様、段階1は暫定値、段階2で最終値に上書きする。 |
| L | 所要時間／時間切れフラグ | 開始から終了までの経過時間、または時間切れによる終了かどうか。段階2では更新しない。 |
| M | 各設問の回答詳細 | 設問ID・区分・小区分・出題形式・回答内容・正誤（選択式）・得点とフィードバック（記述式、Geminiによる採点結果）・模範回答（記述式）をJSON文字列でまとめて格納する。段階1では記述式問題の得点・フィードバックは未確定のため仮の値（0点・「採点中」）で記録し、段階2で最終値に上書きする。 |
| N〜T | 記述式採点1〜7 | 出題された記述式問題（最大7問）ごとに1列を割り当てる。段階1では「採点中」という文字列を仮に記録し、段階2で、当該設問の入力回答・スコア（0〜100点）・参考回答（模範回答）・フィードバックをまとめたJSON文字列で上書きする。出題数が7問未満の場合、余った列は空欄のままにする。 |

### 11-3. 同時書き込みに関する考慮

- 複数の受験者がほぼ同時に「採点」ボタンを押下した場合、スプレッドシートへの追記処理が競合する可能性がある。同様に、複数の受験者の記述式バックグラウンド採点（10-1章 段階2）がほぼ同時に完了した場合も、既存行の更新処理が競合する可能性がある。
- `LockService.getScriptLock()` を用いて、`appendRow`（段階1の追記）・既存行の上書き（段階2の更新）を含む一連の書き込み処理をそれぞれロックし、同時実行による行の欠落・上書きを防止すること。

```javascript
function submitResult(payload) {
  var lock = LockService.getScriptLock();
  lock.waitLock(30000); // 最大30秒待機
  try {
    // 選択式の採点処理・SpreadsheetApp.appendRow 等
  } finally {
    lock.releaseLock();
  }
}

function scoreDescriptiveQuestions(resultId, payload) {
  // 記述式の採点処理（Gemini API呼び出し）はロック取得前に行う
  var lock = LockService.getScriptLock();
  lock.waitLock(30000); // 最大30秒待機
  try {
    // 該当行（resultId）の上書き
  } finally {
    lock.releaseLock();
  }
}
```

### 11-4. 管理者による参照

- 5-1のとおり、管理者は「受験結果」シートを直接開くことで、記録済みデータの一覧・集計・分析ができる。
- 個人情報（氏名・社員番号）を扱うため、当該スプレッドシートの共有設定は、人事・採用担当者等の必要な範囲に限定する。

## 12. 非機能要件

| 項目 | 要件 |
|---|---|
| 対応デバイス | PC・タブレット・スマートフォンのブラウザで問題なく操作できること（レスポンシブ対応）。 |
| ブラウザ | 主要ブラウザ（Chrome、Edge、Safari等）の最新版で動作すること。 |
| アクセシビリティ | チェックボックス・ボタン等はキーボード操作でも選択・押下できること。 |
| データ保護 | 氏名・社員番号などの個人情報を扱うため、Googleアカウントの権限管理・スプレッドシートの共有範囲設定を適切に行うこと。 |
| GAS実行時間制限 | 1回のスクリプト実行は、無料のGoogleアカウントで最大6分、Google Workspaceアカウントで最大30分に制限される。本アプリはGoogle Workspaceアカウントでの運用を前提とする。`submitResult`（10-1章 段階1）は数秒程度で完了する設計とするが、記述式のバックグラウンド採点 `scoreDescriptiveQuestions`（同 段階2）は、Gemini呼び出しの再試行（10-2章、待機時間込みで最大数分）を含めても30分の制限内に収まる設計とする。 |
| GAS同時実行・クォータ | 大量アクセス時のスプレッドシート同時書き込み（11-3のLockService対応）、および1日あたりのスクリプト実行回数等のクォータ上限に留意する。大規模運用（同時受験者数が多い、頻繁に実施する等）が見込まれる場合は、Google Workspaceの契約内容・上限緩和策を事前に確認すること。 |
| 可用性 | タイマー動作中にブラウザの再読み込み等が発生した場合の挙動（再開できるか、最初からになるか）を実装時に定義すること。記述式のバックグラウンド採点（10-1章 段階2）は、受験者が結果画面を閉じる・ブラウザを閉じる等してクライアントとの接続が切れても、GAS側の実行はそれと独立して継続し、採点結果は「受験結果」シートに記録される。 |
| 外部API依存 | 記述式の採点にGemini APIを利用するため、API呼び出しの遅延・失敗が採点処理全体に影響しうる。呼び出しに失敗した場合は10-2章の再試行（最大3回）を行い、それでも失敗した場合は0点として扱い、処理自体は継続する（受験者側は正常に採点完了として扱われる）。記述式問題は1回のリクエストにまとめて送信するため（10-2章）、Gemini APIのレート制限（1分あたりのリクエスト数上限）には抵触しにくいが、失敗時の再試行によりバックグラウンド採点全体の所要時間が数分〜十数分になりうる点に留意する。 |

## 13. 前提条件・制約事項

- 本仕様は、**Google Apps ScriptおよびGoogleスプレッドシートを実装基盤とすること**を前提とする。
- 問題マスタの内容（72問）は別紙「プログラミングスキル判定テスト_問題集」を正とする。問題の追加・修正を行う場合は、7-1のシート列構成（区分・小区分・出題形式・正解番号等の対応関係）を崩さないよう管理すること。
- 選択肢のランダム表示・記述式の配分ロジック（7章・8章）は、出題プールの問題数・記述式比率が変化した場合、按分計算のロジックも見直しが必要となる。
- 受験者区分のURLパラメータ方式（4-1）は、サーバーサイドで検証を行うものの、URLの値自体を受験者が書き換えることによる区分の詐称を技術的に完全には防止できない。厳密な不正防止が必要な業務要件がある場合は、14章に記載のトークン方式等への拡張を検討すること。
- Webアプリのデプロイ設定（「実行するユーザー」「アクセスできるユーザー」）、およびスプレッドシートの共有範囲は、個人情報保護の観点から、開発・運用担当者が責任をもって設定・管理すること。
- 記述式の採点にはGemini API（Google AI Studio発行のAPIキー）を使用する。APIキーはコード内にハードコードせず、GASのスクリプトプロパティ（例：`GEMINI_API_KEY`）に保持すること（`SPREADSHEET_ID`と同様の方針）。使用するGeminiのモデルは実装時に選定する。
- 「受験許可」シート（6-3章）への氏名の登録・削除は、運用担当者が受験案内のタイミングに合わせて行う必要がある。事前登録を失念すると、案内済みの受験者が受験できなくなる点に留意すること。

## 14. 今後の拡張案（参考）

- 受験者区分の詐称・URL使い回しを防ぐため、「区分＋受験者（または受験回）を一意に識別するトークン」を「発行済みトークン」シートで管理し、`doGet(e)` でトークンの有効性を検証した上でのみテストを開始できるようにする方式への拡張。一度使用したトークンは無効化する。
- 社内の受験者（未経験の新入社員／入社3年目までの社員）については、Google Workspaceアカウントでログイン済みであれば `Session.getActiveUser().getEmail()` を用いて氏名・所属を自動取得し、開始画面での入力を省略する仕組みの検討（入社希望者は組織外のためこの方式は適用できない）。
- 受験結果の推移をグラフ化し、同一受験者の複数回受験・成長度合いを可視化する機能（Googleスプレッドシートのグラフ機能、またはGASからGoogle データポータル／Looker Studio等への連携）。
- 管理者向けの簡易サマリー画面（5-1で触れた `?admin=1` 等）へのログイン認証・権限確認機能の追加。
